## (b) Findings by severity

### HIGH

**H1. Reconcile Ineligible Students (owner answer B2-11 = YES) is not built.**
- Repro: `grep -rni reconcile CDC/backend/app CDC/backend/routes CDC/frontend/app CDC/frontend/components` → only `OfferEditService::reconcileFlags`. Probe `test_reconcile_ineligible_students_action_exists` fails.
- Impact: a required owner decision is missing, while `SUPERSET_PARITY_PROGRESS.md` reports S0–S8 complete. D103(d) means ineligible applicants stay in the pool with no admin tool to remove them in bulk.
- Fix: add `GET /admin/postings/{p}/rounds/{r}/reconcile` (re-check every pool member with `EligibilityService::check()` + active `placement_blocks`; return reasons), `GET …/reconcile/export` (formula-safe Excel through `ExportService`, IST footer), and `POST …/reconcile` (`application_ids[]`, confirm). The POST writes **draft** `rejected` rows through `PipelineService::writeDrafts`, or publishes and mails regrets through `dispatchResultMails` (BCC `sendBulk`). Pick one and record it as a D-entry. Audit `round.reconcile`. Add the person-x icon "Reconcile Eligible Students" and a modal "Reconcile Ineligible Students" with "Mark Selected Students As Rejected" on the stage page (Superset labels, analysis 06 F11). Add a progress checklist item and tests.

### MEDIUM
None found.

### LOW

**L1. The "M candidates" counter differs between the Progress Grid and the stage page.**
- Repro: probe `test_shortlist_counter_matches_the_progress_grid_pool_count`. Stage 1 publishes 2 shortlisted. One out-of-pool student is then saved in stage 2 with the D70(b) warning. The grid reads "out of 2 candidates" (`pool_count`, AdminPipelineController.php:58), and the stage page reads "out of 3 candidates" (`counts.candidates`, AdminShortlistController.php:181).
- Fix: either count only in-pool rows in `counts.candidates` and add a separate `outside_pool` count, or make the grid use the same definition. Show "(+1 outside pool)" on the page.

**L2. The same student entered twice is written twice and not reported.** This is a new vector through the email identifier (roll number and email of one student). It is related to the baseline failure T4_2b.
- Repro: probe `test_same_student_by_roll_and_email_is_counted_once_and_reported`. `roll_nos: ['22JE0002', '<22JE0002's email>']` → `written: 2`, no error or warning. With conflicting results in one upload, the last row wins silently.
- Fix: de-duplicate after `resolveEmails` in `AdminPipelineController::results`. Keep the first entry and report the others as "Listed twice".

**L3. Email matching depends on the database collation.**
- `resolveEmails` lower-cases the input but compares it with `whereIn('institute_email'|'personal_email', …)` against the raw column (PipelineService.php:80-83). It works on MySQL `utf8mb4_unicode_ci`, but fails when a stored personal email has capitals on SQLite or any case-sensitive collation (probe `test_email_identifier_matches_a_mixed_case_stored_email_independent_of_collation` fails in the test DB).
- Fix: `whereRaw('LOWER(institute_email) IN (…)')`, or normalise emails on write.

**L4. A custom-template "Download Current Shortlist" has no "Downloaded on … IST" footer.**
- Repro: probe `test_download_current_shortlist_with_a_custom_template_keeps_the_ist_footer`. `TemplateExports::shortlist` (TemplateExports.php:107-134) calls `ExportService::templateWorkbook`, which writes the title row but no footer.
- Fix: add an optional footer to `templateWorkbook` (or append it in `TemplateExports::shortlist`).

**L5. `PATCH /admin/offers/{offer}` re-creates blocks the admin lifted by hand when `apply_blocking` is omitted.**
- Repro: probe `test_type_change_ignores_hand_lifted_blocks_when_the_api_default_is_used`. Lift both blocks through `DELETE /admin/blocks/{id}`, then PATCH `offer_type: intern_fulltime` → 2 active blocks again.
- The dialog protects against this by unticking the box when `had_lifted_blocks` is set (offerdialogs.jsx:52). The API default is `true` (AdminOfferController.php:38,57), so any other client brings the blocks back, against D91 ("a lifted block does not come back unless the admin asks").
- Fix: default `apply_blocking` to `! had_lifted_blocks` on the server, or require the field when `had_lifted_blocks` is true.

**L6. Loose comparison in "Nothing changed."**
- `$current == $changes` (AdminOfferController.php:53) treats `null` and `0` as equal, so changing an empty CTC to 0 returns 422 "Nothing changed." (probe `test_changing_an_empty_ctc_to_zero_is_not_reported_as_nothing_changed`).
- Fix: compare with `===` per key after casting the request through the model casts.

### INFO
- **I1.** The strict label is "Strict check on current stage (refuse students who are not in this stage's pool)". Superset's is "Apply strict check on current stage of applicant" (analysis 06 F8). The default is OFF by owner decision B2-12, which is correct. There is no Roll Number / Email radio (auto-detect is used instead).
- **I2.** The Progress Grid "Excel" button downloads the standard applicants export, which has no overall Status column. Spec S1.6 only says "an Excel button", so this is acceptable, but the file does not show the Status the grid shows.
- **I3.** After a revoke, the final-stage result stays published "Selected" (D109e), so the student's own trail still says "Selected" while they have been mailed that the offer was revoked. This is a design decision, noted for the owner.
- **I4.** `destroyDraft` does not run the `blocked()` check (applications open / cancelled). Only drafts can be removed, so the risk is low.
- **I5.** Selection on the stage page is per page. "Select all" selects only unpublished rows of the current page; selections on other pages are kept but not acted on.
